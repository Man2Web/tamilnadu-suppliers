## 3. Deep Security Analysis of `SECURITY DEFINER` Stored Functions

PostgreSQL `SECURITY DEFINER` functions execute with the privileges of the function's owning role. If configured improperly, they create severe privilege-escalation vulnerabilities.

### Nuance Analysis: Why `SET search_path = public, pg_catalog` Alone Is Insufficient
Per PostgreSQL Security Guidance (Section 38.6):
> Setting `search_path = public, pg_catalog` prevents temporary schema (`pg_temp`) hijacking. However, if untrusted users hold `CREATE` privilege on the `public` schema, an attacker can create a malicious function or operator in `public` with the same name as a built-in system function (e.g. `COALESCE`, `NOW`, `GREATEST`). When a `SECURITY DEFINER` function executes, it will invoke the attacker's Trojan object in `public` instead of `pg_catalog`.

### Forensic Verification of Defense-in-Depth Controls
[`supabase/standalone-postgres-init.sql`](file:///D:/tamilnadu-suppliers/supabase/standalone-postgres-init.sql) implements four interlocking layers of defense:

1. **Schema Privilege Lockdown (Line 847)**:
   ```sql
   REVOKE CREATE ON SCHEMA public FROM PUBLIC;
   ```
   *Analysis*: This strips `CREATE` privilege on `public` from all unprivileged database roles. Untrusted roles cannot create tables, functions, or operators in `public`.

2. **Least Privilege Application Role Grants (Lines 859–866)**:
   ```sql
   GRANT USAGE ON SCHEMA public TO tns_app_user;
   GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO tns_app_user;
   GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO tns_app_user;
   ```
   *Analysis*: `tns_app_user` is granted `USAGE` (to resolve objects) and DML privileges, but **is NOT granted `CREATE ON SCHEMA public`**. Even if the web application were breached via SQL injection, `tns_app_user` lacks database privileges to define new functions in `public`.

3. **Explicit Schema Qualification of Referenced Objects**:
   - `login_rate_limit_status`: `FROM (SELECT 1) AS d LEFT JOIN public.login_rate_limits r ON r.key = p_key;`
   - `login_rate_limit_record_failure`: `INSERT INTO public.login_rate_limits AS t ...` and `DELETE FROM public.login_rate_limits ...`
   - `login_rate_limit_clear`: `DELETE FROM public.login_rate_limits WHERE key = p_key;`
   - `adjust_product_stock_quantities`: `v_prod public.products;`, `SELECT * INTO v_prod FROM public.products ... FOR UPDATE;`, `UPDATE public.products ... RETURNING * INTO v_prod;`
   *Analysis*: All table references and row types explicitly declare `public.<object>`. They do not rely on `search_path` to locate application tables.

4. **Unconditional Revocation of Public Execution (Lines 850–853)**:
   ```sql
   REVOKE ALL ON FUNCTION public.login_rate_limit_status(TEXT) FROM PUBLIC;
   REVOKE ALL ON FUNCTION public.login_rate_limit_record_failure(TEXT, INTEGER, INTEGER, INTEGER) FROM PUBLIC;
   REVOKE ALL ON FUNCTION public.login_rate_limit_clear(TEXT) FROM PUBLIC;
   REVOKE ALL ON FUNCTION public.adjust_product_stock_quantities(VARCHAR, INTEGER, INTEGER, INTEGER, INTEGER) FROM PUBLIC;
   ```
   *Analysis*: In PostgreSQL, `PUBLIC` is granted `EXECUTE` on new functions by default. By placing these `REVOKE` statements unconditionally outside the `DO $$ ...` application role check, public execution is stripped even if `tns_app_user` has not yet been provisioned in the cluster.
